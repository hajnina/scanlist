## Notes

### Lead note 2026-11-16 (research digest: web-rn-runtime-prior-art.md)
- BarcodeDetector: stable in Chrome Android since v83 (requires Google Play Services), NOT in Firefox, flag-gated in Safari, absent on desktop Linux Chrome — feature-detect via `getSupportedFormats()` and bundle zxing-wasm `reader` (~1.04 MiB, MIT) as fallback, or use the `@sec-ant/barcode-detector` polyfill for one code path.
- Frame cadence guidance from 2026 writeups: copy the video frame to a canvas every ~150 ms, `getContext('2d', {willReadFrequently: true})`.
- Build the frame sampler so the JPEG can go EITHER to `/embed/image` (server, C3) OR to an in-browser embedder (spike card C7) — keep the choice behind an interface, the C7 spike may flip it.

### Lead note 2026-11-17 (C3 merged — frame-upload cadence + deferred server nits)
- **Image upload cadence**: server-side image embedding costs 6.4–11.9 s/frame (fp32 CPU, PERF.md). Do NOT upload per camera frame (~2.5 fps) — the queue would back up forever. Design: opportunistic single-frame uploads (e.g. one in-flight image request, newest-frame-wins, or a ~5–10 s cadence), while barcode/OCR text queries stay cheap. The server caps: 2048-char/512-token inputs, LRU 4096.
- Deferred C3-review code nits (low, apply if you touch these files): `app/main.py:110` error body `{"error":{...}}` vs C1's `{"detail":...}` (doc-only for now, README notes it); `last_latency_ms` is shared state — concurrent requests can tag another call's duration (metrics-only distortion); an incomplete HF snapshot (missing config) surfaces as 500 instead of `E_NO_MODEL`; `test_golden_parity.py:57-64` skips on size mismatch instead of failing (a corrupt mount silently skips the gate — check_golden.py still fails hard, so the gate exists); image path returns cached lists by reference vs text path copying.

### Review fix round (ag-c4, 2026-11-17, PR #29 — request-changes)

All four review items fixed; no re-argument.

1. **Blocker — repeat window before the cap (A4-sync parity).** `extractOcrLines` now threads an
   `acceptLine` predicate and applies it in the merged A4-sync order: normalise → drop
   blank/too-short → within-batch dedupe → `acceptLine` (cross-tick repeat window) → count against
   `maxLines` (break after push). `ocrLineSignals` passes `acceptLine: text => dedupe.accept(text,
   now)` and no longer filters after extraction, so suppressed lines consume no cap slots. Read from
   `origin/main:apps/rn/src/scan/sources/ocr.ts` (A4-sync merged as PR #27); no cross-line arithmetic
   and the per-line confidence chain are unchanged.
2. **Discriminating tests (both mutation-verified, then reverted):**
   - **Mutant A — repeat window after the 16-cap (the reviewed bug)**: starvation test fails
     ```
     FAIL  ocr.test.ts > ocrLineSignals > repeat-suppressed lines consume no cap slots (starvation guard, A4-sync parity)
     AssertionError: expected [] to deeply equal [ 'new 0', 'new 1', 'new 2', 'new 3' ]
       - [ "new 0", "new 1", "new 2", "new 3" ]
       + []
     ```
   - **Mutant B — 16-cap before within-batch dedupe**: duplicate-heavy test fails
     ```
     FAIL  ocr.test.ts > extractOcrLines > collapses within-batch duplicates BEFORE the cap (mutant guard)
     AssertionError: expected [ 'Same label' ] to deeply equal [ Array(5) ]
       - [ "Same label", "new 0", "new 1", "new 2", "new 3" ]
       + [ "Same label" ]
     ```
   - New tests: starvation (16 held + 4 fresh on tick 2 → the 4 fresh emit, nothing suppressed
     consumes a slot) and 16 duplicate "Same label" + 4 fresh → all 5 survive in detection order.
     The pre-existing blank/too-short cap test still guards filter-before-cap.
3. **Image emit parity with A4.** `session.ts` no longer emits the image signal at submit time: the
   signal (with `frame.capturedAt`) is emitted from the uploader's `onResult`, immediately before
   `onImageEmbedding`, so a frame replaced while the POST was in flight emits **nothing** and C5 can
   never see an image marker without its vector. New uploader test: slow in-flight POST + a newer
   frame that replaces the pending one + a third that replaces that one → no signal before the first
   response, then exactly frames 1 and 3 emit (frame 2 never appears; `embeddings === [1, 3]`).
4. **Leaks + doc nits.** `stop()` now terminates the Tesseract worker (`ocr.engine.dispose()`; the
   session owns the engine it is handed and is single-use — documented on the option and in the
   README). `start()` releases the camera tracks and clears `video.srcObject` when `video.play()`
   rejects. README manual check now uses `npm run dev` (`preview` cannot serve `/src/...`), cadence

   ~450 ms), the module count is the real 18 modules + 9 test files, and the "capture.ts is the only
   DOM module" claim now also names `session.ts`.
