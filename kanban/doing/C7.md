# C7 — Spike: browser-side EmbeddingGemma 2 via transformers.js + WebGPU

## Do
Research digest (2026-11-16, `/home/martin/projects/scanlist-research/research_notes/ScanList prior art and parallels/web-rn-runtime-prior-art.md`):
transformers.js **4.3.1** (2026-10-07) natively runs `onnx-community/embeddinggemma-2-ONNX` (Apache-2.0) for text AND
images into one 768-d space: text-only q4 = 175 MB, text+vision q4 = 284 MB (load selectively: `audio_config = null`),
**WebGPU required** (WASM is broken for q4/q8 — missing `GatherBlockQuantized` kernel; fp16 fallback ≈1.2 GB — do not
chase it). WebGPU is default-on in Chrome Android 121+ on Android 12+ with Qualcomm/ARM GPUs.

Build a spike page under `apps/web/frontend/src/embed-spike/`: load the model, embed several item doc texts (ts-core
docText + active prefixes) + one camera frame (getUserMedia grab) or a fixture JPEG. Measure ON A REAL PHONE:
download time, load time, text embed latency, per-IMAGE embed latency, and cosine agreement vs `shared/fixtures/golden.json`
vectors (S3) on the same inputs. Mind the traps: batch ≤ ~2700 tokens total (≈9 images at 280 tokens); images take no
prefix; images batch as `[[a],[b]]` not `[a,b]` (flat list = one blended embedding); re-normalise after slicing to 256.
Compare against the `POST /embed/image` server round-trip (C3) if the server is running.

Write `apps/web/frontend/EMBED_SPIKE.md` with the numbers and a clear recommendation: client-side / server-side /
hybrid (e.g. docs server-side cached at import time + images client-side one-shot). The lead will act on it (new card
or C3 scope change).

**Measurements (real model, real WebGPU device, desktop only).** Adapter `qualcomm/adreno-7xx`
(Snapdragon X Elite laptop, Chrome 154 headless with `--enable-unsafe-webgpu --use-angle=vulkan
--enable-features=Vulkan`); each run = one Chrome on one profile, cache verified clean between runs.

- **q4 (the model card's dtype) is unusable here**: 5 attempts (headless, headless + `--disable-gpu-
  watchdog --disable-hang-monitor`, headful under Xvfb) all die with `BufferManager::Download …
  wgpu::MapAsyncStatus … [Device] is lost` ~60–65 s into the first inference; q4 never returns a
  vector, q8 returns exactly one 768-d vector (72.6 s) then loses the device too. That is a measured
  result, not an assumption.
- **fp16 works** (same code, one option): text+vision 878.1 MB / text-only 542.5 MB; warm load
  1.67 s (weights) + 1.12 s (tokenizer/processor) = 2.86 s; cold download 69.2 s (878 MB) / 118.5 s
  (543 MB).
- **Text, canonical `window.__c7.run` report**: cold first embed 196 ms; 10 docs in one batch of 9 =
  200 ms → **22 ms/doc** (total 396 ms); warm single query median **45.6 ms** (p90 47.1); 4-query
  batch 94–99 ms; tokenize 10 docs 4–5 ms.
- **Text parity vs `golden.json`** (fp32 oracle): docs min cos **0.999938** / median 0.999954, queries
  min cos **0.999936** / median 0.999971, max abs diff ≤ 2.9e-3 — and **ts-core `rank()` top-1 matches
  golden for 12/12 text queries**. fp16 in the browser preserves the ranking the app uses.
- **Images are blocked, honestly**: the vision encoder's forward pass never settles. Full suite hit
  the 180 s watchdog on the first image; a dedicated 600 s probe returned nothing after 600,037 ms;
  a staged probe shows `image preprocess (1 input(s)) in 35 ms` and then no forward-pass line for
  150 s. All 15 fixture JPEGs decode in 6–85 ms, so the hang is inside the GPU forward pass (no
  device-lost message, no exception). **No browser image latency or image parity exists** — that is
  reported as blocked, not as a number.
- **WASM checked on-machine**: q4 → session creation fails in ~40 ms with `Could not find an
  implementation for GatherBlockQuantized … /model/embed_tokens/Gather_Quant`. So "no WebGPU" = "no
  q4/q8 model at all", not "slower".
- **Verdict in the doc (§1)**: keep embeddings server-side. Browser text is ~6× the server's
  cache-miss and never beats its 0.04 ms cache hit, at the price of a 543–878 MB download and a hard
  WebGPU gate; the browser image path is unproven (vision pass does not return) so images stay on the
  server. What would change it: a phone run of this page, and q4/q8 working on Android's GPU stack.
